# 200 Skills Later: What I Learned Building an Agentic Operating System

This morning I dispatched 4 AI agents to work in parallel. One scanned Hacker News, another analyzed my 50-project codebase, a third reviewed a GitHub repo's architecture, and the fourth audited my entire skill system. Two crashed before executing a single command. The other two delivered results I couldn't have produced in an hour.

That ratio — half brilliant, half broken — is agentic coding in February 2026. Not the benchmarks. Not the launch demos. The actual, daily, duct-tape-and-markdown experience of running AI agent teams on real work.

## The War Story

The task sounded simple: cross-reference today's HN front page with my codebase, find threads where I could add value, seed blog ideas from the intersection. I split it across a team:

| Agent | Task | Result |
|-------|------|--------|
| hn-scanner | Fetch + analyze HN front page | **Crashed** (tmux corruption) |
| codebase-scanner | Scan 50+ workspace projects | Delivered in ~60s |
| manifest-analyst | Analyze an open-source repo's architecture | **Crashed** (tmux corruption) |
| superpowers-reviewer | Audit 14 superpowers skills | Delivered comprehensive review |

Two out of four. 50% success rate.

The failure was absurd: Claude Code spawns agent teams as tmux pane splits in your current window. With 4 agents splitting simultaneously, `send-keys` got garbled. One agent received `mmcd` instead of `cd`. Another got `mentcd`. Both died with `zsh: command not found`.

The future of agentic coding is bottlenecked by a tmux split-pane race condition. [I filed the bug](https://github.com/anthropics/claude-code/issues/23615).

I finished the crashed agents' work myself in 2 minutes. The task list knew what was done and what wasn't. The surviving agents' output was genuinely excellent — a comprehensive audit of 14 skills, a structured map of 50+ projects. The system degraded gracefully. Not because the agents were reliable, but because the **workflow** was right. When infrastructure breaks, workflow is what catches you.

## Two Companies, Two Bets, Both Wrong

Claude Opus 4.6 and GPT-5.3-Codex both hit HN's front page today. Combined: 3,000+ points. The comment sections are where it gets interesting.

OpenAI wants you to steer. Sit in the cockpit, watch the model work, course-correct when it drifts. Codex is built for that — you interrupt, redirect, keep hands on the wheel.

Anthropic wants you to let go. Describe the destination, let Opus plan the route, check back when it's done. Longer runs, fewer interruptions, trust the model.

Neither company's users agree with the marketing. Opus users complain it ignores their corrections. Codex users say it spirals during long autonomous runs. The models are converging toward a middle ground that neither company designed for.

But the practitioners in those threads — the ones actually shipping with these tools — landed somewhere else entirely. They stopped arguing about how much to steer and started writing down *what good looks like* for their specific work. Guardrails. Verification steps. Architectural checklists. Reusable instructions.

They reinvented skills without calling them that.

## Skills as the Third Path

A skill is a markdown file. That's all.

```markdown
# systematic-debugging
1. Reproduce the bug
2. Form a hypothesis
3. Test the hypothesis
4. If 3 fixes fail, escalate to architectural review
```

No framework, no dependencies, no runtime. Instructions that any capable model follows.

I have 200 of these covering everything from drafting comments to analyzing data to publishing posts. They trigger on what I say, not what I type — asking "will this survive?" fires a survival evaluation skill automatically. Description matching, not slash commands.

The autonomy-vs-steering debate misses the point. Autonomy fails because the model guesses your intent. Steering fails because you become a babysitter. Skills encode your intent once and the model executes it repeatedly. You steer by writing better skills, not by interrupting better.

A philosophy I picked up from the superpowers project crystallized this: **prose first, code only when prose fails.** I tested it directly. Built a TypeScript scoring framework for workspace analysis. Found 6 bugs across 3 severity levels. Rewrote it as a skill — "scan projects, prioritize recent ones" — same result, zero bugs, fraction of the tokens.

Code has bugs. Prose has intent. At 200 skills, I stopped debating which model to use and started investing in better instructions.

## Skillvault: One Skill, Every Agent

200 skills means nothing if they're locked to one tool. Right now my Claude Code skills are invisible to Cursor. Cursor rules don't exist for Copilot. Every AI coding agent invented its own format:

| Agent | Skill Location | Format |
|-------|---------------|--------|
| Claude Code | `.claude/skills/*/SKILL.md` | YAML frontmatter + markdown |
| Codex CLI | `~/.codex/skills/*/SKILL.md` | Same as Claude |
| Cursor | `.cursor/rules/*.mdc` | MDC frontmatter + markdown |
| Copilot | `.github/copilot-instructions.md` | Plain markdown |
| Gemini CLI | `GEMINI.md` | Plain markdown |

So I built [skillvault](https://github.com/anupamchugh/skillvault) — 850KB of Rust that syncs and translates skills across all of them:

```bash
skillvault status                  # What's where
skillvault doctor                  # Health audit (frontmatter, tokens, compliance)
skillvault sync                    # Bidirectional sync, SHA256 hashing
skillvault translate --to cursor   # SKILL.md → .cursorrules
```

`translate` is the thing that matters. Write a skill once for Claude, and skillvault emits Cursor's `.mdc`, Copilot's `copilot-instructions.md`, Gemini's `GEMINI.md`. Same workflow knowledge, every agent.

Nobody talks about vendor lock-in for AI coding workflows. They should. Models change every quarter. Your hard-won debugging process shouldn't be trapped in `.cursor/rules/` when you switch tools next month.

## You Don't Need Agent Teams. You Need Composable Skills.

My 4-agent team was 4 processes in tmux panes. Two died. But the skills that defined their work — `hn-snipe`, `workspace-scan`, `dispatching-parallel-agents` — those are still here. They'll work tomorrow. They'll work in a different agent. They'll work if I run them one at a time instead of four at once.

The skills compose into a pipeline:

```
workspace-scan → hn-snipe → blog-seed → quick-blog
     ↓                ↓           ↓
  "what I built"  "what's hot"  "where they intersect"
```

Run it with real agent teams when tmux cooperates. Run it sequentially in one session when it doesn't. Hand pieces to Codex overnight and review in the morning. The skills don't know or care how they're executed. They describe *what*, never *how to parallelize*.

I've started calling this "pseudo agent teams" — decompose work into skills, compose skills into pipelines, execute however makes sense today. The dependency graph lives in the skill descriptions, not the orchestration layer. When an agent crashes, another picks up the same skill and continues. When the infrastructure changes (and it will, quarterly), the skills survive.

The real agent team isn't the tmux panes. It's the skill graph.

## Memory: The Actual Hard Problem

Model capability isn't the bottleneck. Memory is.

I ran a thorough skill audit this morning. The agent produced a structured review of 14 skills with specific issues and 5 gap recommendations. Genuinely useful. And until I manually saved it, that entire analysis existed only in a chat window. Close the terminal, it's gone.

This keeps happening. HN thread analysis, blog ideas, architecture reviews — all ephemeral by default. The agent generates better output than I could write manually, and then the session ends and it vanishes.

Today I stopped accepting that. Two changes:

**Project-scoped memory.** Claude Code loads a `MEMORY.md` file into every session's system prompt automatically. I turned it into an index linking to topic-specific files:

```
~/.claude/projects/.../memory/
├── MEMORY.md              ← loaded every session
├── hn-snipes.md           ← HN threads to engage with
├── blog-ideas.md          ← posts seeded from HN + codebase
├── superpowers-review.md  ← skill audit results
└── manifest-pattern.md    ← WORKSPACE.yaml docs
```

**A workspace manifest.** `WORKSPACE.yaml` at the project root — any agent landing in my workspace reads this first and knows what exists:

```yaml
version: 1
owner: anupamchugh
philosophy:
  - prose-first
  - survival-tested

trading:
  kite-trading-platform:
    description: Full-stack algo trading (NSE/NFO/MCX)
    stack: [python, fastapi, websocket, polars]
    features: [paper-sim, rrs, telegram-digest]

mcp_servers_count: 8
skills_count: 200+
ios_apps_count: 8+
```

Borrowed from an open-source agentic coding flywheel project, where a single manifest YAML defines every tool with install commands, verification logic, and schema validation. Mine skips the install plumbing — I don't need agents to set up my environment — but the core idea is the same. Give the agent a map before it starts exploring.

## The Takeaway

The autonomy-vs-collaboration argument is a distraction. Both camps optimize for model behavior. The thing that actually matters is your workflow — and workflows are portable when they're prose.

Write down how you debug. How you review code. How you analyze a trading signal. Make it a markdown file with a YAML header. Run it in Claude today, translate it to Cursor tomorrow, hand it to whatever ships in Q3. The model is a runtime. The skill is the program.

200 skills later, that's the only thing I'm confident about. Everything else — the agent teams, the orchestration layers, the context windows — changes every quarter. The workflows survive.
